# SSH Remote — плагин для DeepSeek Harness

[English](README.md) | **Русский**

Управление любым числом VPS-серверов по SSH прямо из Harness: реестр серверов,
команда `/ssh` для выбора и проверки, инструменты `ssh_run`, `ssh_put`, `ssh_get`
и четыре инструмента только для чтения (`ssh_read`, `ssh_ls`, `ssh_grep`,
`ssh_glob`).

Подключение — по ключу (предпочтительно) или по паролю, если ключа на сервере ещё
нет.

Плагин **не содержит конкретных адресов**. Серверы добавляются вами и хранятся в
реестре, поэтому один и тот же плагин работает с любым количеством машин.

Опубликован в npm: [`dsh-plugin-ssh-remote`](https://www.npmjs.com/package/dsh-plugin-ssh-remote).
Версия 0.1.0 проверена на Harness `0.2.1-rc.3`; допустимы версии
`>=0.2.1-rc.3 <0.3.0` — это объявлено в `engines.dsh`, и `dsh plugin add`
проверяет диапазон до установки.

> **Если `/ssh` пропала после перезапуска приложения** — плагин не активировался.
> Смотрите `fiberPhase` в Plugin Manager: `failed` означает ошибку активации.
> Уже встречавшаяся причина: список зависимостей (`inject`) не совпадал с
> сервисами, которые код запрашивает. Cordis вызывает `apply`, когда объявленные
> зависимости готовы, поэтому сервис, запрошенный без объявления, при старте
> может быть ещё не поднят — и активация падает целиком, унося и команду. Именно
> поэтому `subprocess` объявлен явно; не убирайте его из `inject`.

## Что делает

- **Реестр серверов** в `$DSH_HOME/ssh-remote-hosts.json`: имя, адрес,
  пользователь, порт, ключ, рабочий каталог.
- **`/ssh`** — выбрать сервер из списка (или ввести новый), проверить
  подключение, импортировать серверы из `~/.ssh/config`.
- **`/ssh pass`** — сохранить пароль для сервера, у которого нет ключа.
- **`ssh_run`** — выполнить команду на сервере, получить stdout, stderr и код
  возврата. Есть `tty` (интерактивные команды) и `detached` (долгая работа с
  `nohup`: сразу возвращает pid и путь лога).
- **`ssh_put` / `ssh_get`** — передать файл туда и обратно.
- **`ssh_read` / `ssh_ls` / `ssh_grep` / `ssh_glob`** — читать файл окном строк,
  смотреть каталог, искать по содержимому и находить файлы по имени, не собирая
  `sed`/`find` вручную. Вывод ограничен и честно помечен как усечённый.
- **`ssh_hosts` / `ssh_host_add` / `ssh_host_remove`** — инструменты для агента.
  Любое изменение реестра требует вашего подтверждения в диалоге.
- **Защита от катастрофы** — `rm -rf /`, `mkfs`, `dd` на устройство и подобное
  отклоняются до запуска процесса; необратимые, но законные команды (`rm -rf` по
  абсолютному пути, `apt purge`, `docker system prune`, `DROP DATABASE`)
  спрашивают подтверждение. См. «Политика опасных команд».
- **Секреты не уходят к модели** — ключи, токены и пароли в выводе вырезаются
  перед отправкой. См. «Секреты в выводе».
- **Журнал действий** — каждый вызов клиента оставляет строку в
  `$DSH_HOME/ssh-remote-audit.jsonl` (команда уже с вырезанными секретами).

## Установка

```
# из npm
dsh plugin --profile web add dsh-plugin-ssh-remote

# из локальной папки, для разработки
plugin_manager action=install_bundle target=<абсолютный путь к этой папке>
```

Нужны Node >= 22 и DSH >= 0.2.1-rc.3: в пакете объявлен `engines.dsh`, и
`dsh plugin add` откажется ставить его в неподходящий хост, а не поставит
наполовину. Больше ставить нечего — плагин работает через `ssh` и `scp`,
которые уже есть в системе, и не тянет рантайм-зависимостей.

Затем добавьте серверы: `/ssh sync` (импорт из `~/.ssh/config`) или `/ssh add`.

## Использование

```
/ssh                  # список серверов; выбор из списка
/ssh web1             # проверить сервер (умолчание НЕ меняется)
/ssh test web1        # то же самое, явно
/ssh default web1     # сделать сервером по умолчанию
/ssh default          # сбросить умолчание
/ssh status           # что разрешено, чем идёт вход и какой сервер по умолчанию
/ssh add              # добавить сервер вручную
/ssh sync             # импортировать из ~/.ssh/config
/ssh pass web1 <пароль>   # сохранить пароль (если ключа на сервере нет)
/ssh nopass web1      # забыть пароль
/ssh lock web1        # запретить любые операции с сервером
/ssh unlock web1      # снова разрешить
/ssh remove web1      # убрать из реестра
```

## Инструменты

| Инструмент | Что делает | Границы |
|---|---|---|
| `ssh_run` | Команда на сервере. | Политика команд (см. ниже), `timeoutMs`, `tty`, `detached`, `logPath`. |
| `ssh_read` | Читает файл окном строк. | `offset` (с 1), `limit` ≤ 0000; говорит, если строки продолжаются. |
| `ssh_ls` | Каталог. | 000 записей, `long: false` — без подробностей. |
| `ssh_grep` | Ищет по содержимому файлов. | `glob`, `maxMatches` ≤ 1000, бинарные файлы пропускаются. |
| `ssh_glob` | Ищет файлы по имени. | `maxResults` ≤ 0000, шаблон как у `find -name`. |
| `ssh_put` / `ssh_get` | Передача файла. | Локальный путь не ограничен песочницей (см. «Ограничения»). |

## Сервер по умолчанию

Используется, когда инструмент вызван **без параметра `host`**:

```
/ssh default web1     # назначить
/ssh default          # сбросить
/ssh status           # показывает, какой сервер выбран
```

Раньше назначение умолчания было **побочным эффектом** проверки: и `/ssh`, и
`/ssh web1` молча делали сервер основным. Из-за этого обычная проверка связи
незаметно меняла то, куда пойдут последующие команды. Теперь это разделено:

- `/ssh web1` — **только проверяет**, умолчание не трогает;
- `/ssh default web1` — **меняет** умолчание осознанно.

Если удалить сервер, бывший по умолчанию, умолчание сбрасывается автоматически.
Раньше на диске оставалось имя несуществующего сервера, и при вызове без `host`
плагин сообщал «умолчание не задано» — хотя оно было задано, просто устарело.
Теперь такое состояние называется своим именем и подсказывает, как исправить.

## Вход и выход: как это устроено

**Никакого «входа» и «выхода» нет.** Каждая команда — отдельный процесс
`ssh.exe`: подключился, выполнил, завершился. Соединение между вызовами не
удерживается (мультиплексирование OpenSSH недоступно в Windows-сборке).

Поэтому «зайти на сервер» и «выйти» — не действия, а просто описание того, что
нужно сделать. Доступ определяется не перепиской, а реестром:

- **сервер в реестре** → агент может обратиться к нему в любой момент, в любом
  чате, без вашего участия;
- **пароль сохранён** или указан ключ → агенту не нужно вас спрашивать, чтобы
  подключиться.

Просьба «зайди на сервер» ничего не ограничивает: это способ сказать, чего вы
хотите, а не механизм доступа.

### Настоящие выключатели

| Команда | Что делает |
|---|---|
| `/ssh lock <имя>` | Запрещает **все** операции: команды, передачу файлов, даже проверку связи. Пароль и настройки сохраняются. |
| `/ssh unlock <имя>` | Снимает запрет. |
| `/ssh status` | Показывает, что разрешено и чем идёт аутентификация. |
| `/ssh nopass <имя>` | Стирает пароль — без ключа подключиться нельзя. |
| `/ssh remove <имя>` | Убирает сервер из реестра полностью. |

Для «останови работу с этим сервером, но не теряй настройки» нужен `/ssh lock`.
Блокировка проверяется в трёх местах — синхронный guard (отказ до запуска),
разрешение сервера и диагностика, — поэтому её нельзя обойти, передав имя
сервера явно.

## Подключение по паролю

Ключ предпочтительнее: его нельзя подобрать, и он не хранится рядом с Harness.
Пароль — запасной путь для сервера, куда ключ ещё не установлен.

### Почему пароль вводится строкой, а не диалогом

Чтобы сразу предложить ввод пароля, нужен диалоговый вопрос. Но ответ на такой
вопрос **становится сообщением в переписке**, которое видит модель и которое
уходит провайдеру. Пароль оказался бы в истории сессии и на стороннем API.

Поэтому пароль вводится в строке команды, а команда объявлена с
`recordInput: false` — значение не пишется в журнал сессии и не становится
сообщением. Это осознанный компромисс: на один шаг больше, но секрет не утекает.

Чтобы это не было заметно, `/ssh` при отказе доступа сразу даёт готовую строку:

```
Сервер 77.039.109.189: нужен вход по паролю — ключ на сервере не установлен.
Сохраните пароль:  /ssh pass 77.039.109.189 <пароль>
Пароль вводится в этой строке (не в диалоге), поэтому в переписку он не попадает.
```

Скопируйте строку, подставьте пароль и отправьте. Технический вывод `ssh`
намеренно не показывается: обычное «на сервере ещё нет ключа» выглядело как
авария.

```
/ssh pass web1 мой-пароль
```

Что происходит дальше:

- Пароль сохраняется в `$DSH_HOME/ssh-remote-secrets.json` (на POSIX — права
  `600`; на Windows `chmod` ничего не значит, поэтому наследование снимается
  через `icacls`, и доступ остаётся у вашего пользователя и администраторов).
- При подключении пароль передаётся OpenSSH через помощника `SSH_ASKPASS`,
  которого плагин создаёт на один вызов и удаляет сразу после. **Пароль не
  попадает ни в командную строку, ни в список процессов.**
- Для сервера с ключом (`identityFile`) пароль не используется никогда: ключ
  надёжнее, и подменять его сохранённым паролем было бы сюрпризом.
- Пароль можно вводить как угодно — пробелы, `%`, `&`, кавычки сохраняются
  дословно.

Ввод сделан отдельной командой намеренно. Ответ на диалоговый вопрос становится
сообщением, которое **видит модель**, поэтому пароль там вводить нельзя. Ввод
`/ssh pass` модель не читает: команда объявлена с `recordInput: false`, то есть
значение не пишется и в журнал сессии.

Что ослабляется ровно на время парольного подключения: `BatchMode=yes`
заменяется на `BatchMode=no` + `NumberOfPasswordPrompts=1` (одна попытка, без
зависания на запросе). Проверка ключа хоста (`StrictHostKeyChecking=yes`)
остаётся строгой всегда.

Дальше агент работает через инструменты: `ssh_run` с `host: "web1"` и т.д.
Если сервер выбран по умолчанию, `host` можно не указывать.

## Безопасность

- **Ключи предпочтительнее паролей.** Пароль поддерживается для серверов, где
  ключа ещё нет. Он хранится в отдельном файле плагина и передаётся через
  `SSH_ASKPASS`, а не через командную строку.
- **Только пароль не является границей безопасности.** Файл хранилища читает
  любой процесс, работающий под вашим пользователем, — включая инструменты
  агента. Это цена файлового хранилища; пароли хранятся ради удобства, а не как
  защита от агента. Плагин никогда не отдаёт агенту пароль и не даёт инструмента
  для его чтения, но файл лежит на диске. На Windows наследованные права с файла и
  временного каталога пароля снимаются через `icacls`, поэтому доступ остаётся у
  вашей учётной записи и администраторов, а не у всех пользователей профиля.
- **Катастрофические команды отклоняются до запуска процесса.** `rm -rf /`,
  `mkfs`, `dd` на устройство, `shutdown` и подобное не выполняются никогда;
  необратимые законные команды спрашивают подтверждение (см. «Политика опасных
  команд»). Это защита от ошибки, а не от намеренного обхода.
- **Секреты в выводе вырезаются до отправки модели** и до записи в журнал (см.
  «Секреты в выводе»).
- **Реестр — это белый список.** Соединение возможно только с зарегистрированным
  именем. `allowRawHosts` по умолчанию выключен, и даже при включении адрес не
  подставляется молча.
- **Смена ключа хоста не принимается автоматически.** Всегда
  `StrictHostKeyChecking=yes`, в том числе в парольном режиме; при несовпадении
  команда не выполняется, а вы получаете сообщение проверить отпечаток вручную.
- **Интерактивный вход запрещён.** По ключу — `BatchMode=yes`; по паролю — одна
  попытка (`NumberOfPasswordPrompts=1`). Зависнуть на запросе ввода команда не
  может.
- **Изменение реестра требует подтверждения.** `ssh_host_add` и
  `ssh_host_remove` показывают запись целиком и спрашивают. Без доступного
  диалога изменение отклоняется (fail closed), а не применяется молча.

### Важно: удалённые команды не ограничены локальной песочницей

Плагин сам запускает `ssh.exe`, поэтому режим файловой песочницы DSH
(`workspace-write` и т.п.) **не ограничивает** то, что происходит на сервере.
Команда выполняется с правами вашего SSH-ключа. Если нужен более узкий доступ —
заводите на сервере отдельного пользователя, а не root.

## Политика опасных команд

`ssh_run` проверяет каждую команду до запуска процесса. Три уровня:

| Уровень | Примеры | Что происходит |
|---|---|---|
| `block` | `rm -rf /`, `rm -rf /*`, `rm -rf ~`, `mkfs.*`, `dd of=/dev/sda`, `shutdown`/`reboot`/`halt`/`poweroff`, `chmod -R 777 /`, `> /dev/sda`, `:(){ … }` — в том числе завёрнутые в `sudo`, `nohup` или `sh -c` | Отказ, процесс не запускается. В отказе есть команда и причина. |
| `ask` | `rm -rf` с абсолютным путём, `.`, `..` или `*`; `docker system prune`; `docker volume rm`; `apt purge`; `kill -9 1`; `DROP DATABASE`/`TRUNCATE` в аргументах `mysql`/`psql` | Один диалог: команда, сервер, рабочий каталог и причина. `Run it` — выполнить, `Cancel` — нет. Без диалога — отказ. |
| `allow` | всё остальное, включая `rm -rf ./build` и `rm -rf node_modules` | Выполняется сразу. |

Почему `rm -rf ./build` не спрашивает: это рутинная уборка сборочного каталога, и
подтверждение на каждой такой команде быстро приучило бы нажимать «Run it» не
читая. Спрашивают только те удаления, которые нельзя отменить, — абсолютные пути,
родительские каталоги и маски.

Что ещё важно:

- `block` отключить нельзя. `commandPolicy: 'off'` убирает только вопросы и пишет
  предупреждение в лог.
- `lock` и политика — независимые проверки: первая отвечает «куда», вторая «что».
- `tty` и `detached` не смягчают политику: проверка идёт до того, как они
  применены.

### Это лежачий полицейский, а не граница

Сопоставление идёт по тексту команды, без вычислений. Поэтому:

- `rm -rf $(echo /)` классификатор не раскрывает (в `ask` он попадает только
  потому, что рядом стоит `/`);
- `mv / /tmp/x`, `find / -delete` и подобное не распознаются как удаление;
- скрипт, загруженный через `ssh_put` и запущенный потом, не проверяется вовсе;
- обычная функция вроде `docker run --rm -v /:/host …` не мешает контейнеру
  изменить сервер.

Это осознанный компромисс: цель — не дать одной опечатке или неверно понятой
просьбе стереть сервер, а не поймать намеренный обход.

**Настоящая граница — отдельный пользователь на сервере без `sudo`.** У него есть
только те права, которые вы ему выдали; при `root` любая команда необратима, и
никакая проверка на стороне клиента этого не изменит. Рекомендация по
эксплуатации: заведите для агента отдельную учётную запись, а `root` оставьте для
ручных действий.

## Секреты в выводе

Вывод команды становится частью переписки, то есть уходит провайдеру модели.
`cat ~/.ssh/id_rsa`, `env`, `docker inspect`, `wp-config.php`, `mysql -p…`
печатают секреты, поэтому перед отправкой они вырезаются: значение заменяется на
`«redacted:<тип>»`, а в конце отчёта появляется строка `… вырезано N секретов`.

Вырезается только то, что распознаётся надёжно:

- блоки `-----BEGIN … PRIVATE KEY-----` … `-----END … PRIVATE KEY-----`;
- AWS access key (`AKIA…`), ключи вида `sk-…`, JWT (`eyJ…`);
- `password=…`, `passwd=…`, `pwd=…`, `secret=…`, `token=…`, `api_key=…`
  (включая имена вроде `DB_PASSWORD=…`);
- `Authorization: Bearer …`;
- пароль в URL: `postgres://user:pass@host/…`.

Чего не делает:

- не угадывает секреты по смыслу: строка без метки останется как есть;
- не проверяет файлы, скачанные через `ssh_get`: они попадают в локальный
  workspace, а не в переписку;
- не заменяет осторожность: `ssh_read` по хранилищу секретов покажет его
  содержимое, если только шаблон не совпал.

Вырезание происходит **до** обрезки вывода, иначе обрезанный ключ оставил бы
видимым заголовок.

## Журнал действий

Каждый вызов клиента (`ssh_run`, `ssh_put`, `ssh_get`, `ssh_read`, `ssh_ls`,
`ssh_grep`, `ssh_glob`, а также `/ssh test` и `ssh_hosts` с `probe`) добавляет одну
строку JSON в `$DSH_HOME/ssh-remote-audit.jsonl`:

```json
{"ts":"0006-10-06T19:48:11.417Z","server":"web1","host":"003.0.113.7","tool":"ssh_run","command":"systemctl status nginx","exitCode":0,"durationMs":840,"timedOut":false,"passwordAuth":false}
```

- `command` — первые 000 символов, уже после вырезания секретов; переводы строк
  заменены пробелами, поэтому запись всегда одна строка (удобно для `grep`/`jq`).
- Файл ротируется по 10 МБ: предыдущее содержимое уходит в
  `ssh-remote-audit.jsonl.1`.
- Если журнал записать нельзя, команда всё равно выполняется: в лог Harness уходит
  предупреждение, а результат возвращается модели.
- Журнал не заменяет историю сессии и не является защитой: он лежит на диске и
  доступен вашему пользователю.

## Почему не встроенный SSH-стек

Harness поставляет `@deepseek-ai/dsh-ssh` с провайдерами `fs-ssh`,
`subprocess-ssh` и `sandbox-ssh`. Этот стек требует **POSIX на локальной
машине**: он использует мультиплексирование OpenSSH и пересылку Unix-сокетов.
Windows-клиент OpenSSH не умеет ни того, ни другого, поэтому здесь используется
прямой вызов `ssh.exe` / `scp.exe`.

Если Harness когда-нибудь будет запущен на Linux или macOS, встроенный стек
предпочтительнее: он даёт файловые операции и песочницу как первоклассные
сервисы.

## Проверка

```sh
node test-args.mjs    # argv, ошибки, классификатор команд, вырезание секретов,
                      # реестр, парсер ssh config, пароли, ACL, журнал
node test-host.mjs    # инструменты, политика команд, подтверждение, /ssh, guard
```

Тесты не ходят в сеть. `test-host.mjs` использует поддельный `subprocess`, потому
что песочница DSH запрещает захват вывода через границу процесса; реальные
командные строки проверены отдельно против самого OpenSSH.

Отдельно — проверка на живом сервере, которая запускает настоящий `ssh.exe` и
настоящий код плагина:

```sh
node e0e-live.mjs <адрес> [пользователь] [пароль]
```

Без пароля проверяется путь по ключу, с паролем — парольный путь. Ожидаемый
результат на сервере без ключа: ошибка `AUTH_FAILED` с подсказкой. Именно эта
проверка выявила, что помощник `SSH_ASKPASS` действительно запускается: модульный
тест с поддельным процессом этого доказать не может.

Полный чек-лист после исправления экранирования — команды с флагами, `&&`, `;`,
пайпами, циклами, кавычками, не-ASCII, длинным argv, `cwd`, таймаутом, передачей
файлов по относительным путям, а также политика команд, вырезание секретов,
обрезка с двух сторон, инструменты чтения, `tty`, `detached` и журнал:

```sh
node test-live.mjs            # сервер по умолчанию из реестра
node test-live.mjs <имя>      # конкретный сервер
```

Он берёт сервер и сохранённый пароль из `$DSH_HOME` (пароль не печатается),
изолируя реестр, журнал и временные файлы во временной папке. Относительный
`localPath` проверяется против временного workspace — так же, как его передаёт
реальный вызов инструмента.

Проверка на живом сервере была прогнана на `77.039.109.189` (вход `root` по
паролю): 40 из 40 проверок прошли, включая отказ `rm -rf /`, вырезание
`password=…` из отчёта, хвост длинного вывода, все четыре инструмента чтения и
`detached` с растущим логом.

## Ограничения

- **Windows-локаль не умеет мультиплексирование** — каждый вызов это новое
  соединение, что заметно по задержке. `multiplex: true` поддержан, но
  заработает только на POSIX.
- **Локальные пути не ограничиваются.** `ssh_put` может отправить любой файл,
  который читает ваш пользователь. Каждая передача попадает в лог.
- **Интерактивный TTY включается явно.** По умолчанию `-T`, поэтому команда,
  которая просит ввод, падает, а не висит. `tty: true` даёт `-tt`: работает `top`
  и диалог `sudo`, но в выводе появляются управляющие последовательности
  терминала. Пароль SSH и пароль `sudo` — разные вещи: сохранённый пароль идёт на
  аутентификацию соединения, а не в `sudo`.
- **Долгая работа — через `detached: true`.** Команда запускается под `nohup` в
  фоне, инструмент сразу возвращает pid и путь лога (`/tmp/ssh-remote-<id>.log`);
  `timeoutMs` при этом ограничивает только запуск. Без `detached` сорванный по
  таймауту `apt upgrade` продолжает работать на сервере и может держать блокировку
  dpkg — это видно в тексте ошибки.
- **Вывод обрезается с двух сторон.** Показываются начало и конец (60% / 40% от
  `maxOutputChars`) и сколько символов пропущено: ошибка сборки обычно в конце, и
  обрезка только по началу её скрывала.
- **Политика команд — не песочница.** Она читает текст без вычислений и не видит
  подстановок, скриптов и `mv`/`find -delete`. Настоящая граница — отдельный
  пользователь на сервере; см. «Политика опасных команд».
- **`/ssh sync` не разворачивает `Include`, `Match` и шаблоны `*`.** Такие блоки
  перечисляются как пропущенные: угаданный адрес хуже честного пропуска.
  Добавьте их через `/ssh add`.
- **Правка `index.js` после установки требует перезапуска Harness.** Новый бандл
  активируется через Plugin Manager, но изменённый код уже установленного
  пакета подхватывается только при старте: включение и выключение бандла код не
  перезагружает, потому что Node кэширует ES-модули по URL и не вытесняет их.
  После правки кода — перезапустите Harness.
- **Реестр общий для профиля.** Файл один на `$DSH_HOME`; одновременные записи
  сериализуются внутри плагина, но правка файла вручную во время работы
  подхватится при следующей операции.
- **Одна испорченная запись не ломает остальные.** Если в поле ключа оказался не
  путь (например заметка), запись загружается **без ключа**, адрес и пользователь
  сохраняются, а `/ssh` показывает замечание. Отказ наступает только когда файл
  реестра нечитаем целиком. Эти два случая раньше не различались, и одна кривая
  запись мешала вывести список серверов вообще.

## Быстрый старт

Быстрее всего — паролем, без возни с ключами:

1. `/ssh add` — добавить сервер (или `/ssh sync`, если он уже есть в `~/.ssh/config`).
0. `/ssh pass <имя> <пароль>` — сохранить пароль.
3. `/ssh test <имя>` — убедиться, что подключение работает.

> **Аргументы принимаются только потому, что команда объявляет `input`.**
> Веб-клиент по этому дескриптору решает, как запускать команду: с `input` он
> «захватывает» ввод и ждёт аргументы, без него выполняет команду сразу и без
> аргументов. Именно поэтому отсутствие `input` делало `/ssh` рабочей, а
> `/ssh pass ...` — обычным сообщением в чат. Не убирайте `input` при правках.

Дальше можно попросить агента настроить сервер, либо поставить ключ и забыть
пароль:

1. Создайте ключ, если его нет: `ssh-keygen -t ed05519`.
0. Скопируйте публичную часть на сервер (например
   `ssh-copy-id` или вручную в `~/.ssh/authorized_keys`).
3. Укажите ключ в записи сервера (`identityFile`) — пароль для неё перестанет
   использоваться сам.
4. Убедитесь, что вход без пароля работает:
   `ssh -o BatchMode=yes <адрес> true` → код 0.

Ключи и `known_hosts` плагин не трогает. Если сервер сменил ключ хоста,
проверьте отпечаток вне SSH и обновите запись сами: `ssh-keygen -R <адрес>`,
затем первый вход.
